# Release Types

ForgeOps uses the following release strategy.

## Major

Introduces breaking changes or significant architectural improvements.

Example:

```text
1.0.0
2.0.0
3.0.0
```

---

## Minor

Introduces new features while maintaining backward compatibility.

Example:

```text
1.1.0
1.2.0
1.3.0
```

---

## Patch

Introduces bug fixes and small improvements.

Example:

```text
1.2.1
1.2.2
1.2.3
```

---

# Versioning Policy

ForgeOps follows Semantic Versioning.

```text
MAJOR.MINOR.PATCH
```

Where:

| Component | Description      |
| --------- | ---------------- |
| MAJOR     | Breaking changes |
| MINOR     | New features     |
| PATCH     | Bug fixes        |

# Release Process

Each release should follow these steps:

1. Complete development on the `develop` branch.
2. Create a `release/x.y.z` branch.
3. Perform testing and validation.
4. Update documentation.
5. Update this CHANGELOG.
6. Create a Git tag.
7. Publish the GitHub Release.
8. Merge into `main`.
9. Merge back into `develop`.
